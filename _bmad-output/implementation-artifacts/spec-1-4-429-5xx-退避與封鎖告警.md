## Intent

**Problem:** `limitedFetch`（`src/limiter.ts`）遇 429/5xx 已有遞增延遲重試，但重試耗盡後仍為封鎖回應時，只會把該回應原樣交還給呼叫端；上層（`src/sources/usj.ts` 的目錄取樣迴圈、`src/fetcher.ts` 的逐產品迴圈）目前對任何錯誤一律「記一筆失敗、繼續下一項」，導致持續被來源封鎖時該回合不會停止，也不會讓 job 以非 0 exit code 結束（NFR8 / AD-16 #1 未落實）。

**Approach:** 在 `limitedFetch` 重試耗盡後，若最後一次回應仍為 429/5xx，改為 throw 一個可識別的 `BlockedError`（而非回傳該回應）；`usj.ts` 目錄取樣迴圈與 `fetcher.ts` 逐產品迴圈的既有 catch 區塊新增例外處理：偵測到 `BlockedError` 時不得比照一般錯誤吞掉繼續，須立即中止整個回合並以非 0 exit code 結束。

## Boundaries & Constraints

**Always:** 遞增延遲重試（`RETRY_DELAYS_MS = [1000, 2000, 4000]`，現行已符合 exponential backoff）行為維持不變，且須補上回歸測試鎖定「延遲遞增」這件事，避免未來被悄悄改成固定延遲。`BlockedError` 只在 `limitedFetch` 重試迴圈本身判定「耗盡重試後仍為 429/5xx 回應」時拋出——這是唯一的「持續封鎖」判定點，不得在 `usj.ts`／`fetcher.ts` 另立第二套判定邏輯。單一產品的一般錯誤（如個別商品 404、解析失敗）不得因本次變更被誤判為封鎖而中止整回合（AD-16「單一產品失敗仍不紅」須保留）。偵測到 `BlockedError` 時的處理只能是「立即停止、非 0 exit」，不得改用降級重試、切換端點或其他繼續抓取的手段（NFR8）。

**Block If:** 無需人工決策——判定條件（重試耗盡且最後一次仍 429/5xx）與應對方式（停止＋非 0 exit）在 epics.md AC 與 AD-16 #1 中已明確。

**Never:** 不得新增外部告警管道（email/webhook 等）——AD-16 明訂告警機制即「非 0 exit 觸發 GitHub Actions 內建失敗通知」，不得新增其他管道。不得把一般連線層錯誤（`fetch()` 本身 throw，例如斷線）也判定為 `BlockedError`——AC 描述的是「連續收到封鎖回應」，即已收到 HTTP 回應但狀態碼持續為 429/5xx，與底層連線失敗是不同的錯誤類別，本 story 不擴大 `BlockedError` 的觸發範圍。不得變更 `RATE_LIMIT_PER_SEC`／`CONCURRENCY`／`MAX_REQUESTS_PER_RUN` 等 AD-4 互鎖常數。

## Tasks & Acceptance

**Execution:**
- `src/limiter.ts` -- 新增並 `export class BlockedError extends Error`（攜帶造成封鎖的 `url` 與最後一次 `status`）；修改 `limitedFetch` 第 102-103 行，重試耗盡且仍 `retryable` 時 throw `BlockedError` 而非 `return res` -- 把「退避後仍連續收到封鎖回應」鎖成可被上層識別、可回歸驗證的訊號
- `src/sources/usj.ts` -- `listProducts` 的目錄取樣 catch 區塊新增 `if (err instanceof BlockedError) throw err;` 分支 -- 避免目錄取樣把「持續封鎖」誤判為單一取樣失敗而吞掉繼續，讓錯誤傳遞到既有的 catalog 失敗處理（`fetcher.ts` 既有 `process.exit(1)`）
- `src/fetcher.ts` -- 逐產品迴圈的 catch 區塊新增 `if (err instanceof BlockedError) { console.error(...); process.exit(1); }` 分支 -- 落實 NFR8「該回合須立即停止，不得改以其他方式續抓」與 AD-16 #1「job 須以非 0 exit code 結束，觸發 GitHub Actions 內建失敗通知」
- `src/limiter.test.ts`（新檔）-- 新增測試涵蓋 I/O Matrix 的四個情境：429 重試後成功、連續封鎖直到耗盡（斷言延遲遞增且最終 reject 為 `BlockedError`）、不可重試狀態碼（如 404）維持既有行為、以及 `BlockedError` 可被 `instanceof` 辨識 -- 把本 story 的兩項 AC（遞增延遲、持續封鎖判定）鎖為可回歸驗證的不變量

**Acceptance Criteria:**
- Given 抓取請求收到 429 或 5xx, when `limitedFetch` 重試, then 重試延遲須遞增（exponential backoff，即 `RETRY_DELAYS_MS` 依序套用，不得改為固定延遲）
- Given 退避後（重試耗盡）仍連續收到封鎖回應（429 或 5xx）, when `limitedFetch` 判定為持續封鎖, then 該次呼叫須以 `BlockedError` reject，不得回傳該封鎖回應交由呼叫端誤判為一般錯誤
- Given `listProducts` 目錄取樣或 `fetcher.ts` 逐產品迴圈的任一次請求最終拋出 `BlockedError`, when 該錯誤傳遞到迴圈的 catch 區塊, then 整個回合須立即停止（不得繼續處理其餘取樣日期或其餘產品），不得改以其他方式續抓
- Given 整個回合因 `BlockedError` 中止, when process 結束, then exit code 須為非 0，觸發 GitHub Actions 內建失敗通知（AD-16 #1），且本回合不得寫入 `index.json`／`days.json`（上一份成功快照保留，NFR11）
- Given 單一產品發生非 `BlockedError` 的一般錯誤（如個別商品解析失敗）, when 逐產品迴圈的 catch 區塊處理該錯誤, then 既有行為不變：記 `failed++`、寫入帶 `error` 欄位的 summary、繼續處理下一產品（AD-16「單一產品失敗仍不紅」須保留，不得被本次變更波及）

## Design Notes

`BlockedError` 的判定點刻意收斂在 `limitedFetch` 內部（唯一出口閘門，AD-3），而不是在 `usj.ts`／`fetcher.ts` 各自重新判斷狀態碼——四個 `limitedFetch` 呼叫點與目錄取樣共用同一個判定邏輯，避免未來新增呼叫點時忘記比照處理。`usj.ts` 現有的 `if (!res.ok) throw new Error(...)` 四處呼叫點不需改動：因為封鎖情境現在已在 `limitedFetch` 內被攔截並以 `BlockedError` reject，不會再有「重試耗盡仍 429/5xx」的 `Response` 流到這些既有的 `!res.ok` 檢查。

`fetcher.ts` 逐產品迴圈選擇直接 `process.exit(1)`（而非 rethrow 讓 `main()` 的呼叫端處理），是因為該迴圈本身沒有外層 try/catch、`main()` 也未被包在 `.catch(...)` 呼叫下——直接呼叫 `process.exit(1)` 比依賴 unhandled rejection 的預設行為更明確可控，且與現有 catalog 失敗路徑（`fetcher.ts:212-215`）的既有風格一致。

### 殘餘風險

- 併發取樣（`mapLimit`，並行度 4）偵測到封鎖後，其餘在途請求仍會各自跑完重試序列才失敗——「立即停止」在併發情境下有偵測延遲（已列管於 `deferred`）。
- 封鎖中止的回合，中止前已寫入的 `data/products/*.json` 仍會被 `if: always()` 的 commit 步驟提交，與未更新的 `index.json` 不一致；站台以 `index.json` 為讀取入口故實際讀不到，但 git 會累積這批檔案（已列管於 `deferred`）。
- `if (require.main === module)` 閘門目前正確（CommonJS + ts-node，已實測），但無測試或 CI 冒煙確認；工具鏈改為 ESM／改用其他 runner 時會靜默無作為（已列管於 `deferred`）。
- 封鎖偵測範圍依 intent 明文限縮於「已收到 HTTP 回應且狀態碼為 429/5xx」；以 403、200 challenge page 或直接斷線方式實施的封鎖不會被判定為 `BlockedError`。
