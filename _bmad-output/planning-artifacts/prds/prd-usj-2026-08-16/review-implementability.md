## 1. 模稜兩可（同一句話可實作成兩種材質不同的東西）

### A1 — FR1「單一畫面矩陣」的「畫面」是什麼

> **FR1** 系統須在單一畫面呈現「日期 × 票種」的可購狀態矩陣，使用者無須逐一點入即可跨日期、跨票種比較。

- **讀法一（真矩陣）**：一張 23 欄 × 63 列（或轉置）的表格，1,449 格同時在 DOM 裡，使用者靠捲動瀏覽。
- **讀法二（一軸鎖定）**：任一時刻只呈現「一天 × 23 票種」或「一票種 × 63 天」的一維列表，靠 FR2 的切換走完另一軸——這正是 `index.html:1003`~`:1006` 目前的 `tabProduct` / `tabDate` 分頁做的事。

兩種讀法的成本差一個數量級（讀法一要虛擬捲動與 CWV 調校，讀法二幾乎是現況重排）。FR2「兩種閱讀主軸，並可由使用者切換」其實暗示讀法二（真矩陣不需要切換主軸，轉置只是視覺），但 FR1 的「矩陣」字面又指向讀法一。**PRD 必須挑一個。**

### A2 — FR2「切換」是切換版面還是切換資料

「依日期」與「依票種」在資料層是兩份不同的檔案：`data/days.json`（`fetcher.ts:124`~`:154` 由產品檔轉置而來）與 `data/products/<code>.json`。前者 65KB 一次載完，後者單檔 18KB~491KB。若讀成「切換版面」，兩軸都要能離線轉置，就必須把兩份資料都載進來；若讀成「切換資料視角」，就沿用現況的按需載入（`index.html:1022`、`:1282`）。**這個選擇直接決定 P1 靜態預渲染要產出幾個頁面。**

### A3 — FR4「可調整的設定值」的調整者是誰

> 門檻初始值為 **10 張**，須為可調整的設定值而非寫死於版面邏輯。

- **讀法一**：程式碼裡一個具名常數（開發者改，重新部署）——最省。
- **讀法二**：使用者可在 UI 上調（像現有的人數加減器 `index.html:1169`~`:1174`）。
- **讀法三**：外部設定檔／環境變數（維運可改，不動程式碼）。

現況把「少量」門檻寫死成 `item.units != null && item.units <= 5`（`index.html:1052`），而 `tight` 用的是使用者選的人數（`index.html:1037`）。PRD 要的是哪一種沒說。

### A4 — FR6「大幅橫向捲動」沒有量詞

> 使用者須能在**不進行大幅橫向捲動**的前提下完成跨日期或跨票種比較。

「大幅」不可判定。現況已有一條刻意做的水平捲動日期條（`.date-strip`，`index.html:93` `overflow-x: auto`；`index.html:1189`、`:1264` 用 `scrollIntoView({inline:'center'})` 把選中日捲進視野）。這條算不算「大幅」？NFR16 更進一步說「**不得依賴**橫向捲動」——見 §3 C1，兩條的強度不一致。

### A5 — FR13「獨立且可被索引的 URL」的形狀未定

`/`、`/ja/`、`/en/`？還是 `/zh-TW/index.html`？還是 query string？FR24 要求「URL 與實體命名須穩定」但沒給命名規則。這會連動 FR14 的 canonical 值、FR17 的 sitemap 條目、以及 P1 預渲染腳本的輸出路徑。**開發者只能自己發明一套，之後改動即是 SEO 事故。**

### A6 — FR16 / NFR19「核心內容不執行 JS 可讀」的深度未定

- **讀法一**：只要首屏（預設語言、預設日期）在 HTML 裡。
- **讀法二**：整個 1,449 格矩陣、三語，全部在 HTML 裡。

讀法二的體積：目前 `days.json` 是 65KB 壓縮前 JSON，攤成 HTML 標記後每語言約 200KB~400KB，三語 × 每語一頁。這與 NFR18（CWV/LCP）直接打架。PRD 用 `[ASSUMPTION]` 把它推給架構階段，但「推給架構階段」的前提是 PRD 至少界定了範圍，這裡沒有。

### A7 — FR22「每個事實陳述」的粒度

> 每個事實陳述須明確標示**資料擷取時間與時區**。

一格一個時間戳（928 個），還是一頁一個？現況資料支援前者：每個票種有 `fetchedAt`（`types.ts:96`），每個日期的時段有 `slotsFetchedAt`（`types.ts:56`），全站有 `index.updatedAt`（`types.ts:163`）。三個時間戳語意不同且會差到 6 小時（見 C4）。PRD 只提 `updatedAt`（FR18），卻在 FR22 要求「每個事實陳述」——兩者不一致。

### A8 — NFR9「kill switch」的機制未定

「可立即停用抓取的開關」可以是：workflow 的 `workflow_dispatch` 手動停用、repo variable 檢查、commit 一個 `PAUSED` 檔案、或直接關掉 Actions。「並記錄啟用程序」的「記錄」是寫進 README、還是產出稽核 log？**在一個「上線前必須能當日停止」的法遵需求上，這個模糊度不可接受。**

## 3. 衝突（不能同時成立，或互相拉扯）

### C1 — FR2 雙主軸矩陣 × FR6/NFR16 行動裝置不橫向捲動 【嚴重】

規模是硬事實：23 票種 × 63 日 = **1,449 格**（`data/index.json` 23 products；`data/days.json` 63 days）。在 375px 寬的螢幕上，即使每格壓到 40px 寬也只放得下 9 欄。

- 若 FR1 讀成真矩陣 → 必然橫向捲動 → 違反 FR6/NFR16。
- 若讀成一軸鎖定（現況的分頁）→ 沒有「矩陣」，FR1 的字面失守，而且**「一個畫面內看完跨日期 × 跨票種」（§2 目標一）在行動裝置上本來就不可能**——這是產品定位與物理版面的衝突，不是實作技巧問題。

更麻煩的是 NFR16 比 FR6 更嚴格：FR6 說「不進行**大幅**橫向捲動」（容許少量），NFR16 說「**不得依賴**橫向捲動」（不容許）。而現況的日期條就是橫向捲動元件（`index.html:93`、`:1151`、`:1189`）。**PRD 需要決定：核心比較是否允許橫向捲動，以及矩陣的日期軸最多呈現幾天。**

### C2 — FR16/NFR19 免 JS 核心內容 × 現行架構 × 資料寫入節制設計 【嚴重】

PRD 已承認架構落差（FR16 的 `[ASSUMPTION]`、R5），但漏掉了第二層衝突：**預渲染要把資料烘進 HTML，而整條 fetcher 的寫檔策略是圍繞「內容沒變就不要進 git」設計的。**

- `fetcher.ts:66`~`:73` `writeProduct()` 只在 `contentKey()` 改變時寫檔；
- `fetcher.ts:58`~`:64` `contentKey()` 特意剝掉 `fetchedAt` / `slotsFetchedAt`，註解直白寫著「否則每次都會看起來變了，把整份重寫塞進 git」；
- `fetcher.ts:162`~`:180` `serializeDays()` 把每個「票種 × 日」壓成一行，註解寫著「這是阻止它主宰 repo 成長的關鍵」。

一旦 P1 改成「建置時預先產出靜態內容」，每回合（每 30 或 60 分鐘）都要重生三語 HTML 並 commit。**上述所有節制立刻歸零，repo 每天新增數十次數百 KB 的 HTML diff。** PRD 沒有任何需求處理「預渲染產物要不要進 git／要不要另建部署管線」。而且 repo 裡**根本沒有部署工作流程**：`git ls-files` 只有 `.github/workflows/fetch.yml` 一個；`package.json` 的 `build` 只是 `tsc`。P1 要新建的東西比 PRD 寫的多一整條管線。

### C3 — FR25 廣告版位 × NFR18 CLS 【中】

> **NFR18** …廣告版位（FR25）不得造成版面位移。

AdSense 的 responsive / auto ads 在未預留固定高度時必然造成 CLS。「不得造成版面位移」只有一種實作方式：**為每個版位預留固定尺寸的佔位盒**。但 FR25 的 `[NOTE FOR PM]` 說「版位的數量與位置待定」——尺寸未定就無法預留，NFR18 就無法在 P3 交付時滿足。兩者必須同時定案，PRD 卻把它們分開（FR25 待定、NFR18 硬性）。

另一層：NFR17 說「不使用干擾性插頁廣告」，這是 AdSense Auto Ads 預設會插的格式之一；PRD 沒要求關閉 Auto Ads 的 vignette/anchor。

### C4 — NFR4 降速 × NFR5 回合長度 × NFR5.2 逾時 × 30 分鐘 cron 【中；但 PRD 的算術本身有誤，見 F6】

PRD 的推導鏈是：降速到 1 req/s → 冷啟動由 10 分鐘變 50 分鐘 → 超過 30 分鐘 cron 間隔 → 必須改 hourly 且 `timeout-minutes` 拉到 55。這條鏈**內部自洽**（NFR5.2 補得很好），但**它的起點數字（冷啟動 ~3000 請求 / 10 分鐘）與程式碼算出來的不符**——詳見 §4 F6。若真實冷啟動約 870 請求，1 req/s 下約 15 分鐘，那麼 30 分鐘 cron 仍滿足 NFR5 的「不超過間隔一半」，整套 hourly + timeout 55 的「共同解」是**基於錯誤前提的過度修正**。

真正該擔心的衝突 PRD 沒抓到：**每 6 小時的強制時段重刷**（見 F7）。

還有一個被 hourly 方案打到的隱性常數：`index.html:287` `STALE_MS = 90 * 60 * 1000`，其上一行註解明寫「Fetcher runs every 30 min; 90 minutes of silence means something is wrong」。**把 cron 改成 hourly 而不改這個常數，FR19 的過期警示就會在正常運作時誤報（僅需 1.5 次漏跑）。** PRD 的 P0「三個值必須成套變更」少算了第四個值。

### C5 — §3 新鮮度目標「庫存摘要 ≤ 1 小時」× NFR4~NFR6 共同解的 hourly cron 【中】

若 cron 是整點跑、回合耗時 15~50 分鐘，資料的最大延遲 = 間隔 + 回合耗時 = **75~110 分鐘 > 1 小時**。§3 的成功指標與 §7 的建議配套直接互斥。（GitHub Actions 排程本身還有數分鐘~數十分鐘的排隊延遲，會再放大。）

### C6 — §6 開頭「不呈現逐時段明細」× NFR6「保住分層排程」 【中】

§6 開頭把粒度釘死在「日期 × 票種」，FR5 只要時段**數**。但 `slots` 這個數字只是 `timeSlots.length`（`fetcher.ts:139`）——取得它必須跑完最貴的那一層：每日一次 `getExpressPassVariantDetails`（`usj.ts:592`）。而 `fetchSlotStock()`（`usj.ts:278`~`:312`，每回合再加數十個 POST）取得的**逐時段剩餘張數**，在新粒度下**沒有任何需求會用到**。

於是 NFR6「保住這個設計不被回歸」與 §6 的減法互相矛盾：
- 照 §6 做 → `fetchSlotStock` 與 `TimeSlot.availableUnits`（`types.ts:38`）成為純浪費，佔冷啟動請求量的可觀比例；
- 照 NFR6 做 → 保留一層沒有需求消費的資料。

PRD 也沒說現有的**人數篩選功能**（`index.html:1029`~`:1031` `fitsParty()`、`:1153`~`:1157` 人數加減器）與**逐時段畫面**（`.slot-grid` / `.slot-detail`，`index.html:152`~`:176`）要不要移除。§5「明確排除」表沒有列它們。**這是一次未被聲明的功能刪除。**

### C7 — FR12 語言選擇跨造訪保留 × FR13 三語獨立 URL 【小】

現況把語言存在 `localStorage`（`index.html:507`、`:1345`）。改成 `/ja/`、`/en/` 這類獨立 URL 後，「保留」有三種互斥實作：(a) 進站時依 localStorage 自動導向——會讓 Googlebot 抓到跳轉、破壞 FR13/FR14 的索引意圖；(b) 只在切換器上高亮記住的語言、不導向——那使用者體感上沒被「保留」；(c) 依 `Accept-Language` 導向——靜態託管做不到。PRD 沒指定，而 (a) 與 FR13 是實質衝突。

### C8 — FR20 / NFR13~NFR15 的階段歸屬互相矛盾 【小】

§9 把「非官方聲明」放在 **P0**（`NFR13~NFR15`），同時把 **FR20**（同一件事的 FR 版本）放在 **P2**。而 P1 會把 `index.html` 整個重寫成預渲染架構。**在 P0 往現行 CSR 頁面裡塞三語聲明，會在 P1 被丟掉重做。** 要嘛把 NFR13~NFR15 移到 P1，要嘛接受一次刻意的重工——PRD 沒說是哪個。

### ❌ 錯誤或過時的斷言

#### F1 —「可購狀態矩陣」的前提不成立：資料裡沒有「售完」 【最嚴重】

FR3 要求每格呈現「可購狀態與剩餘張數」，§2 的 SEO 論述整條建立在「售完 / 売り切れ / sold out / 在庫」這組長尾字上。但：

- `fetcher.ts:132` `buildDays()` 明寫 `if (!date.available) continue;` — **`days.json` 只收可購的日期**；
- 更關鍵：**23 個產品檔共 928 筆日期列，`available: false` 的有 0 筆**。API 的行事曆端點在該日該票種賣完（或未開賣）時，根本不回傳那一列（`usj.ts:515`~`:518` 直接把回傳的 `calendarDates` 映射過來，`usj.ts:162` 的 `available` 判定實務上永遠為 true）。

**結論：目前的資料管線無法區分「售完」「尚未開賣」「該票種當日不販售」三者——它們一律表現為「格子不存在」。** 一個宣稱呈現「可購狀態」的矩陣，其最有價值的那個狀態（售完）在資料裡是缺席的，不是 false。PRD 完全沒有察覺這一點，也沒有需求要求補上。這會反噬 FR1、FR3、FR12（不得暗示售完為永久）、NFR12，以及整個 SEO 策略。

#### F2 — FR5 對 `slots: null` 的語意判斷錯誤 【嚴重】

> **FR5** …當 `slots` 為 `null`（**無時段概念**）時須有明確且不同於「0 個時段」的呈現。

程式碼說的是相反的事：
- `types.ts:143` `slots: number | null; // time slots known for that day; null = not fetched`
- `types.ts:51` `timeSlots: TimeSlot[] | null; // null = not fetched for this date`
- `fetcher.ts:139` `slots: date.timeSlots ? date.timeSlots.length : null`
- 「無時段概念」的票種（walk-up）**根本不會進到資料裡**：`fetcher.ts:246`~`:250` 在 `!result.deep` 時直接刪檔並 `continue`；`types.ts:120` 註解「Always true — walk-up passes never make it into the index」。

**`null` 的真正意思是「這一天在 `SLOT_WINDOW_MONTHS = 1` 的滾動窗之外，我們沒去問」**（`usj.ts:555`~`:560`）。目前 `days.json` 裡 386 個 `null` 對 542 個有數字者——**約 42% 的格子是「未取得」而非「無時段概念」**。照 FR5 的字面實作，會對這 386 格顯示錯誤的訊息。

而且這帶出一個 PRD 沒回答的問題：**矩陣有超過四成的格子沒有時段數，要怎麼呈現？** 擴大 `SLOT_WINDOW_MONTHS` 會直接放大請求量，與 NFR4/NFR5 對撞。

#### F3 — FR3「剩餘張數（`units`）」的「null = 未公開」路徑是死路 【中】

`types.ts:142` 註解 `units: null = not exposed`，`index.html:1039`~`:1041` 也有 `dayUnitsUnknown`（「剩餘張數未公開」）的三語字串。但 `data/days.json` 裡 **`"units":null` 出現 0 次**——USJ 對每個可購日都給精確數字。這不是錯誤，但 PRD 把 FR3 寫得像 `units` 可能缺席，實際上只要格子存在，數字就一定存在。**真正會缺席的是格子本身（F1）。**

#### F4 — R5「`<html lang>` 寫死 `zh-TW`」不精確 【小，但影響 FR15 的工作量估算】

`index.html:2` 確實是 `<html lang="zh-TW">`，但 `applyLocaleChrome()` 在執行期同時改掉 `lang` 與 `title`：

- `index.html:616`~`:618`：`document.documentElement.lang = locale; document.title = t('title');`
- 三語標題已存在：`index.html:313`、`:374`、`:435`

所以「寫死」只對**不執行 JS 的爬蟲**成立（這正是 FR16 的痛點），對使用者不成立。同理，R5 說「無標題」也不對——`index.html:6` 有 `<title>`，只是它是單語靜態值。**FR15 要新做的是 meta description 與「靜態」的 per-language lang/title，不是從零做語言切換。**

#### F5 — NFR8「須以遞增延遲退避」已經實作，PRD 卻沒標為現況 【小】

`limiter.ts:28` `RETRY_DELAYS_MS = [1000, 2000, 4000]`，`limiter.ts:74`~`:103` 對 429 與 ≥500 遞增退避，且**退避期間持續佔住 gate**（`limiter.ts:100`~`:102` 的 `finally { release() }`）——註解 `limiter.ts:69`~`:71` 明說這是刻意的。PRD 把 NFR8 整條列為 P0 待做，實際上只有後半段「**遇到持續封鎖須停止該回合並告警**」是新工作：現況在重試耗盡後只是丟出錯誤、記 log、繼續跑其他票種（`fetcher.ts:255`~`:272`），只有全部票種都失敗才會 exit 1（`fetcher.ts:314`~`:317`）。**沒有任何「偵測到持續封鎖 → 中止整回合」的邏輯。**

#### F6 — 冷啟動請求量與耗時的估算過高約 3~4 倍 【中，且是 NFR5/NFR5.2「共同解」的地基】

PRD 稱「暖機約數百個請求、冷啟動約三千個」「冷啟動約 10 分鐘」「降速後約 50 分鐘」。依程式碼結構逐項計算（23 個票種，2026-08-16 起算）：

| 項目 | 請求數 | 依據 |
|---|---|---|
| 目錄抽樣 | ~27 | `usj.ts:427` `everyNthDay(start, start+6mo, 7)`，6 個月 ≈ 184 天 ÷ 7 |
| 每票種產品資訊（ja + en） | 23 × 2 = 46 | `usj.ts:488`、`usj.ts:502`（`NAME_LANGS = ['en']`，`usj.ts:36`） |
| 每票種行事曆 | 23 × 1 = 23 | `usj.ts:515`~`:518`（整個 6 個月一次 POST） |
| 時段清單（冷啟動時每個窗內日期各一次） | ~23 × 31 ≈ 713 | `usj.ts:592`，窗寬 `SLOT_WINDOW_MONTHS = 1` |
| 逐時段剩餘量批次 | ~23 × 2~3 ≈ 60 | `usj.ts:283`~`:287`，`STOCK_BATCH_SIZE = 100`（`usj.ts:59`） |
| **合計** | **≈ 870** | |

- 在 5 req/s 下：**≈ 3 分鐘**（PRD 說 10 分鐘）
- 在 1 req/s 下：**≈ 15 分鐘**（PRD 說 50 分鐘）

暖機回合的**下限**（目錄 + 產品資訊 + 行事曆，這三層每回合都全取）= 27 + 46 + 23 ≈ **96 個請求** → 5 req/s 下約 20 秒（與 PRD 的「不到 1 分鐘」相符），1 req/s 下約 1.6 分鐘（PRD 說 2~5 分鐘，也大致相符）。

**影響**：若冷啟動實際是 15 分鐘而非 50 分鐘，則
- NFR5「不超過間隔一半」在 `*/30` cron 下**降速後仍然滿足**（15 < 15，臨界；用 hourly 則寬鬆）；
- NFR5.2 的「25 分鐘逾時會砍斷冷啟動」**不成立**（15 < 25）；
- §7 那段「三個值必須成套變更，缺一個就壞」的結論**建立在錯誤的量級上**。

同時，`MAX_REQUESTS_PER_RUN = 6000`（`limiter.ts:26`）是實際冷啟動量的**約 7 倍**——這個「煞車」在目前目錄規模下永遠不會踩到，NFR5 把它當成有效上限是誤判。

**建議**：P0 開工前先跑一次 `npm run fetch` 讀 `fetcher.ts:304`~`:308` 印出的實測 `requestCount()` 與 req/s，用真實數字重寫 NFR5/NFR5.2 的現況段。這是 5 分鐘的工作，卻決定了 P0 要不要改三個值。

#### F7 — 最關鍵的負載事實 PRD 完全沒抓到：**每 6 小時會有一次接近冷啟動的重回合** 【嚴重】

`usj.ts:604`~`:609`：一次回合裡所有被刷新的日期共用**同一個時間戳**（`const stamp = new Date().toISOString()`，註解自陳這是刻意的，避免「錯開下次強制回補」）。配合 `slotsAreStale()` 的第三個條件（`usj.ts:419`，超過 `MAX_SLOT_AGE_MS = 6 小時`就重取），結果是：**每個票種的整個時段窗會同時到期，於是每 6 小時就有一個回合要重跑那 ~713 個時段請求。**

在 `*/30` cron 下這是 **12 回合中的 1 個**——不是 PRD 想像的「一次性冷啟動」，而是**每天 4 次的常態尖峰**。NFR5 的現況分析把回合分成「暖機 / 冷啟動」兩類，漏了這個中間類別，而它才是「持續請求速率」在稽核上真正的樣貌。降速到 1 req/s 後，這個 6 小時尖峰回合約 15 分鐘，仍在 30 分鐘間隔內，但**在 `timeout-minutes: 25` 之下沒有多少餘裕**。

#### F8 — NFR3「不複製官方的敘述文字」與現況相反 【中】

`legalDesc`（涵蓋設施的 HTML 敘述文字）被完整抓取（`usj.ts:448`）、存進每個產品檔（`types.ts:85`）、並在頁面上原樣渲染（`index.html:952` 的 `richText(term(src.legalDesc))`）。同時 `i18n/terms.zh-TW.json` 與 `terms.en.json` 是**針對這段敘述文字的人工翻譯表**（`i18n-check.ts:74` 把 `legalDesc` 列為受檢來源）。PRD 把 NFR3 寫成「目前符合」的樣子（放在 P0，未標現況落差），實際上這是一項需要決策的**移除工作**，且移除會讓 `i18n/` 大半的術語表失去用途。

#### F9 — 相對地，PRD 未提到的既有實作（會影響「P2 是中等規模」的估算）

## 5. 缺漏的需求（開發者只能自行發明）

1. **售完狀態的取得方式** 【阻斷級】— 見 F1。要讓「可購狀態矩陣」有意義，必須先決定：(a) 接受「格子缺席 = 不可購」並在 UI 上這樣呈現（但無法區分未開賣）；(b) 另尋端點取得售完日；(c) 由歷史資料推斷（某日曾出現過、現在消失 = 售完）。(c) 需要新的資料保存需求，PRD 完全沒有。
2. **矩陣的日期範圍** — `MONTHS_AHEAD = 6`（`fetcher.ts:9`）但 USJ 實際只開放到 **2026-10-17**（約 62 天，`data/products/*.json` 的 `last`）。矩陣要顯示 62 天？30 天？使用者可選？沒有需求。
3. **票種在矩陣上的排序與分組** — 現況用 `eyebrow` 分組 + `groupRank()` 由大到小（`index.html:963`~`:980`），日內用價格排序（`fetcher.ts:149`）。FR10 說「相同的排序邏輯」，但沒定義排序邏輯是什麼。23 個票種在矩陣的一軸上要不要摺疊？
4. **部署與託管管線** 【阻斷級】— repo 內**沒有任何部署 workflow**（`git ls-files` 僅 `fetch.yml`）；`package.json` 的 `build` 是 `tsc`。P1 要求「建置時預先產出靜態內容」，但沒有需求說明：預渲染在哪跑（fetch workflow 之後？獨立 workflow？）、產物是否進 git、託管在哪、網域是什麼。FR13/FR14/FR17 都需要知道**絕對 URL**才寫得出 canonical 與 sitemap。

6. **`legalDesc` 的去留**（見 F8）與隨之而來的 `i18n/` 術語表命運。
7. **既有功能的刪除清單**（見 C6）— 逐時段畫面、人數篩選、`fetchSlotStock` 這三件事是保留、還是移除？若移除，`SLOT_WINDOW_MONTHS`、`MAX_SLOT_AGE_MS` 這兩個常數的意義也隨之改變。
8. **`STALE_MS` 與 cron 的耦合**（見 C4）— FR19 的「新鮮度門檻」PRD 沒給數值，而程式碼裡的 90 分鐘是綁 30 分鐘 cron 推導出來的。

## 6. 分階段的合理性（P0 → P3 真的能照這個順序蓋嗎）

**整體判定：P0 可行且應先做；P0.5 位置正確；P1 在 P2 之前是錯的順序。**

### P0 — 法遵護欄 ✅ 大致可行，但有三處要修

1. **NFR5.2 的加入是正確且重要的**——「降速、逾時、cron 三者成套」抓到了一個真實的失敗模式。但三個值的具體數字建立在 F6 的錯誤估算上，**應先跑一次實測再定值**（`fetcher.ts:304`~`:308` 已經會印出 `requestCount()` 與實測 req/s，成本是 5 分鐘）。
2. **漏了第四個值**：`index.html:287` 的 `STALE_MS = 90 分鐘`（見 C4）。改 cron 不改它 → FR19 誤報。
3. **NFR13~NFR15 不該在 P0**（見 C8）——它們是 UI 工作，而 P1 會重寫整個 UI。放 P0 = 保證重工。建議移到 P1（預渲染的模板裡一次做掉）。
4. NFR6 現況已符合，P0 對它只是「不要改壞」——這其實是一條**測試需求**（回歸防護），不是實作需求。PRD 沒要求任何測試，而 repo 裡也**沒有任何測試檔**。要「保住這個設計不被回歸」，就得有東西擋著。

### P0.5 — 條款查證 ✅ 位置正確

人工作業、可與 P1 並行、且被正確標為上線前必須。無異議。

### P1 — 搜尋可見性 ⚠️ **順序有實質問題**

P1 要「建置時預先產出靜態內容」。但**預渲染的對象是 P2 才會設計出來的矩陣**。照現在的順序，P1 只能預渲染「現在這個頁面」（單一票種／單一日期的分頁式介面），然後 P2 重做版面時，**預渲染管線的輸出結構要跟著重寫一次**。

這不是理論風險：預渲染的檔案切分方式（一頁一語言？一頁一日期？一頁一票種？）**完全由矩陣的資訊架構決定**，而那是 P2 的產出。FR13（URL 結構）、FR14（canonical/hreflang 對象）、FR17（sitemap 條目）三條需求全都依賴那個結構。

同時 P1 還被 F1 卡住：預渲染出來的靜態內容裡，「可購狀態」欄位目前只有一種值。**把一個資訊不完整的頁面推去給搜尋引擎索引，比晚一點索引更糟**（SEO 上，早期以殘缺內容被索引會拖累後續評分）。

**建議的順序**：
- 把 P2 的**資訊架構決策**（矩陣長什麼樣、URL 怎麼切）提前到 P1 之前，作為一個小的「P0.75 — 版面與 URL 結構定案」；
- 把 F1（售完狀態）當成 P1 的前置阻斷項，因為它同時決定資料形狀與頁面內容；
- P1 與 P2 的實作可以合併成一個階段（預渲染管線 + 矩陣版面一起做），這比先做一次再重做便宜。

PRD 給的理由（「P2 的價值必須有人看得到才成立」）本身沒錯，但它推導出的結論應該是「**不要在版面定案前就把架構鎖死**」，而不是「先做 SEO 再做版面」。

### P2 — 庫存看板 ⚠️ 規模被低估

被標為「中」。但它含著 C1（行動裝置矩陣，可能無解）與 F1（資料裡沒有售完狀態，需要新的取得策略），這兩項都不是版面工作。另一方面，FR8/FR12/FR18/FR19/NFR11 已經完成（見 F9），所以真正的工作量集中在少數幾條硬需求上。**「中」這個估算是把已完成的與無解的兩堆抵銷後的巧合，不是分析結果。**

### P3 — 廣告 ⚠️ 與 NFR18 的相依方向相反

P3 被標為「小，但依賴 P1 帶來的流量」。**真正的相依是反過來的**：NFR18 要求版位不造成 CLS，這只能靠在版面上預留固定尺寸盒達成，而版面在 P2 定案。若 P2 交付時沒有替 P3 預留位置，P3 就必然造成 CLS，NFR18 在 P3 之後失守（見 C3）。

**建議**：把「廣告版位的數量、位置與尺寸」提前到 P2 定案（只留空盒不放程式碼），P3 只做「把 AdSense 程式碼填進既有的空盒」。這樣 P3 才真的是「小」。

### 階段覆蓋完整性 ✅

現版本 §9 的 FR/NFR 覆蓋已無缺口：FR1~FR25 全部落在某個階段（FR18~FR20 已補入 P2），NFR1~NFR19（含 NFR5.1、NFR5.2）亦然。這是相對前一版的改進。
